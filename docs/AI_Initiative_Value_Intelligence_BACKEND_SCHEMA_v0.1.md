1. Purpose

This document defines the logical PostgreSQL schema for V0/MVP. It translates the PRD, application flow, evidence model and TRD into canonical entities and relationships. It is not final SQL DDL; implementation migrations may refine indexes, constraints and types after engineering spikes.

The schema is designed so that later data cannot silently rewrite what leadership believed, approved or decided at an earlier point in time.

2. Schema Principles

Internal UUIDs are canonical; external provider IDs are mappings.

Every tenant-owned record is scoped to organization_id directly or through an enforced parent.

Approved/decision-critical meaning is version-preserved.

Recommendations and human decisions are separate entities.

Raw source data, normalized observations and evidence are distinct layers.

Data quality, evidence strength and recommendation support are separate concepts.

Financial facts and modeled value remain distinguishable.

Manual edits and overrides are auditable.

JSONB is used for flexible metadata, not as a replacement for important relational columns.

Hard deletion of decision/audit history is avoided except where privacy/legal requirements demand controlled deletion.

3. Naming and Type Conventions

Primary keys: UUID generated by application/database.

Timestamps: timestamptz in UTC.

Money: numeric/decimal plus ISO currency code; never floating point.

Metric numeric values: numeric/decimal where precision matters.

Provider identifiers: text with unique constraints where appropriate.

Statuses: PostgreSQL enum or constrained text decided during implementation; values must be migration-safe.

Flexible non-critical metadata: jsonb.

Soft archival: archived_at where product semantics require preservation.

created_at / updated_at on mutable domain records.

created_by_user_id / updated_by_user_id where attribution matters.

25. Tenant Integrity Rules

All tenant-owned child records must match the parent organization's organization_id.

Prefer composite foreign keys or service/database constraints where practical to prevent cross-tenant relationships.

All tenant collection queries begin from authenticated organization scope.

Unique business keys include organization_id unless globally unique by design.

Vector retrieval always filters tenant/access scope before ranking.

Object storage keys/policies are tenant-scoped.

Background jobs carry organization_id and validate it before mutation.

Audit tests attempt cross-tenant reads and writes.

27. Deletion and Retention Semantics

Archiving an initiative does not delete evidence, decisions or audit history.

User deletion/anonymization must preserve required organizational decision records while honoring privacy obligations.

Raw source files may have shorter retention than normalized observations/evidence if policy allows.

Deleting a source file must not silently invalidate historical recommendation snapshots; retention design must preserve sufficient provenance or mark unavailable evidence.

Organization deletion requires a controlled workflow across database, object storage, vector data, credentials, logs and backups.

Exact retention periods are deferred to SECURITY_PRIVACY and customer/legal requirements.

28. Example Relationship Walkthrough

Northstar creates AI Support Automation. initiatives stores the initiative. initiative_versions preserves the submitted business case. investments and investment_cost_items represent the $300,000 plan. metric_definitions/metric_versions define cost per case and CSAT. initiative_metrics marks cost/case PRIMARY_KPI and CSAT GUARDRAIL. baselines store $8.40 and 91%.

CSV data enters through source_files and ingestion_runs. Canonical observations store case counts, costs and CSAT periods. Derived cost/case observations reference calculation versions. A CSAT threshold breach creates product behavior and may contribute evidence. claims/evidence represent what can be said about the change. At review time, review_snapshots freeze the decision context. recommendations stores SCALE plus conditions/support state. decisions separately records what the executive actually chooses. decision_expectations and outcomes later measure whether the scaling decision worked.

32. Acceptance Criteria

Every tenant-owned record has a defensible organization scope.

Clerk IDs are mappings, not canonical domain primary keys.

Metric meaning and baselines can be version-preserved.

Observations retain period, scope and provenance.

Evidence can support, conflict with or contextualize a claim.

Recommendation history does not overwrite the human decision.

SCALE WITH CONDITIONS is represented without inventing a new recommendation type.

Post-decision expectations and outcomes can be compared.

Financial values use decimal + currency.

Manual/import/AI-originated information can be audited.

Historical review context can be reproduced after later data changes.

Schema can support Core Scenario #1 without a graph DB, warehouse or dedicated vector DB.
